# ADR-0002：持久化与依赖装配方式

- 状态：已接受
- 日期：2026-10-26
- 相关：所有服务的仓储、`cmd/*/main.go`

## 背景

项目初始技术栈列出了 sqlc（SQL 生成类型安全代码）与 google/wire（编译期依赖注入）。
实际落地 M0/M1 时，两件工具都没有被引入：

- `go.mod` 中没有 sqlc 或 wire；
- identity 的仓储是手写 `pgx` 查询；
- 服务装配是 `cmd/*/main.go` 里的显式函数调用。

这是事实层面的偏离，不能靠文档措辞掩盖。现在需要决定 M2 及之后怎么做。

## 决策

M1、M2 保持当前方式：

1. **仓储使用手写 pgx**。SQL 显式写在仓储文件里，方法一律接收
   `pgx.Tx`，事务边界由 service 控制。
2. **依赖装配使用普通函数**。`cmd/<service>/main.go` 显式创建
   `db → token issuer → service → handler → routes`，错误立即返回。
3. **M2 不进行工具迁移**。在业务功能尚未完成时同时更换持久化与装配方式，
   会把"功能错误"和"重构错误"混在一起，定位成本很高。
4. **在 M6 之前重新评估**：要么正式引入 sqlc/wire 并补 ADR，
   要么从项目对外口径中删除这两项，不再声称使用。

## 理由

- 当前事务里需要执行 `set_config` 设置租户上下文；手写 tx 流程更容易
  把"设置上下文 → 业务 SQL → 提交/回滚"放在同一处，也方便集成测试审计。
- 服务只有六个，装配依赖有限，手工装配的可读性不差，失败路径也更直观。
- 引入 sqlc 会带来生成代码、配置与迁移同步的额外维护面；在没有明确收益前
  不值得在 M2 打断进度。

## 影响

- 没有编译期 SQL 校验，必须靠集成测试覆盖关键查询（RLS、状态机、预算）。
- 仓储会出现一定样板代码；要求仓储只做 SQL 与扫描，不承载业务判断。
- 简历/项目说明中不得写"使用 sqlc / wire"，除非后续真正落地。
- 该偏差同时记录在 `docs/PROGRESS.md` 风险 28。

## 被否决的方案

1. **M2 立即切 sqlc + wire**：与功能开发交织，回归范围不可控。
2. **继续声称已使用**：与代码事实不符，评审时一查即穿。
