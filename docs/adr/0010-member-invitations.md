# ADR-0010：成员邀请与一次性接受链接

- 状态：已接受
- 日期：2026-10-27
- 相关：identity 服务、notification 内部邮件接口、网关公开路由、管理台成员页

## 背景

风险 35 记录了 M1 的实际缺口：注册接口一次创建"租户 + owner"，之后没有
任何自助入组方式。由于自审批被禁止，真实审批链路必须有第二个成员，而此前
只能由运维直接写库补成员。M10 要补上这条产品路径，同时不能放松已有的
租户边界：

1. 被邀请人通常还没有账号，接受页必须公开可访问；但公开接口不能泄露
   任意租户的成员或邮箱是否存在。
2. 邀请链接一旦泄露就等于入组凭据，必须可撤销、可过期、只能用一次，
   且数据库里不能存明文。
3. identity 不直接发邮件：notification 已有发件箱、重试与 SMTP 配置
   （ADR-0006）。邀请邮件必须复用这条链路，而不是新增第二条发信路径。
4. 接受邀请时会切换当前租户会话。对已有 Expensio 账号的邮箱，如果只凭
   链接就发放该租户的会话，转发一封邮件就能把别人的账号带进另一个租户。

## 决策

### 1. 令牌与存储

- 明文令牌：32 字节 `crypto/rand`，base64url 编码，只出现在创建响应与
  邮件链接里，不落库、不进日志。
- 数据库只存 SHA-256 摘要（`app.invitations.token_hash`，唯一）。
  查询用常量时间等价的摘要匹配，不接受"按明文找行"。
- 同一租户同一邮箱最多一条待接受邀请（部分唯一索引
  `(tenant_id, lower(email)) WHERE accepted_at IS NULL AND revoked_at IS NULL`）。
- 再次邀请会先撤销旧的待接受邀请再插入新行，因此旧链接立即失效；
  撤销是软删除（`revoked_at`），保留审计与状态解释能力。
- 默认有效期 7 天（`EXPENSIO_INVITE_TTL`），允许 1 小时到 30 天。
  过期按读取时判定，不依赖后台清理任务。
- 状态机只有四种可解释状态：待接受、已接受、已撤销、已过期。
  查询/接受分别返回 `410` + `invitation.accepted|revoked|expired`，
  未知令牌返回 `404`。区分"曾经存在但已失效"与"从未存在"是有意的：
  前者能告诉被邀请人该找谁重发，且令牌本身就是凭据。

### 2. RLS 与令牌解析

`app.invitations` 使用 `ENABLE ROW LEVEL SECURITY`（不是 `FORCE`），
并提供 `SECURITY DEFINER` 的 `app.find_invitation(p_hash bytea)`：

- 接受邀请前没有租户上下文，只有链接里的令牌；必须先按摘要找到
  `tenant_id` 才能开事务。这与 `email_outbox` / `claim_emails` 是同一模式。
- 函数只返回接受页所需的字段（租户名、邮箱、角色、有效期、状态），
  不返回其他成员信息。
- 其余读写（创建、列表、撤销、接受）都走普通的租户事务，
  运行时账号仍是 `NOBYPASSRLS`；`FORCE` 会让函数在无上下文时查不到行，
  所以这里显式选择 `ENABLE` 并把风险限制在单个函数上。

### 3. 接受流程必须验证密码

- 邮箱没有全局账号：接受时设置密码与显示名，创建用户、成员关系，
  发放该租户会话。
- 邮箱已有全局账号：必须输入该账号的原密码，验证通过后复用原用户，
  在当前租户创建/激活成员关系，再发放该租户的会话。
- 两种情况都不允许"只凭链接"入组。这样即使链接被转发，接收者也无法
  接管已有账号；同时避免了"邀请即重置密码"的隐性权限提升。
- 接受在租户事务内锁定邀请行（`FOR UPDATE`），只允许一次成功；
  并发点击的第二个请求得到 `410`，不会创建第二个成员。
- 被邀请邮箱若已是该租户的 active/disabled 成员，创建邀请直接
  `409 member.already_member`，不产生无效链接。

### 4. 权限矩阵

| 操作 | owner | admin | member | viewer |
| --- | --- | --- | --- | --- |
| 创建邀请（非 owner 角色） | 是 | 是 | 否 | 否 |
| 创建 owner 邀请 | 是 | 否 | 否 | 否 |
| 查看待接受邀请 | 是 | 是 | 否 | 否 |
| 撤销邀请 | 是 | 是 | 否 | 否 |
| 查询邀请信息（公开） | 持有链接即可 | | | |
| 接受邀请（公开） | 持有链接且通过密码校验 | | | |

邀请创建与接受都写审计（`member.invited` / `member.invitation_accepted`），
元数据只含邮箱与角色，不含令牌或链接。

### 5. 邮件投递

- identity 通过 `HTTPNotifier` 调用 notification 的
  `POST /api/v1/internal/emails`，载荷带 `{tenant_id, exp}` 的 HMAC
  短时令牌；通知服务用签名里的租户写入 `email_outbox`。
- 邮件入队发生在邀请事务提交之后。入队失败不回滚邀请：管理员仍会拿到
  一次性链接，响应里 `email_queued=false`，前端提示手动转发。
- 网关只公开 `/api/v1/invitations`（IP 限流，不需要登录），
  `/api/v1/internal/*` 永不转发。
- 邮件正文只含链接、租户名与有效期；不回传"该邮箱是否已有账号"。

### 6. 前端

- `/invite/:token` 是公开路由；页面先查询邀请信息，再按
  `account_exists` 切换"设置密码"与"输入原密码"两种表单。
- 成员页只在 admin/owner 可见（沿用 `adminOnly` 路由元数据），
  创建成功后弹窗展示一次性链接与复制按钮；待接受列表显示状态、有效期
  与撤销操作。
- 链接只在创建响应里出现一次；列表接口不返回链接，也不返回明文令牌。

## 后果

- 新租户不再需要运维写库就能形成真实审批链路；`member.invited` 与
  `member.invitation_accepted` 可在审计日志中追溯。
- 邀请链接是 bearer 凭据：拿到链接的人仍可为**新邮箱**设置密码入组。
  这是产品可接受的最小摩擦；对已有账号则被密码校验挡住。若未来要求
  更高保证，可增加邮箱验证码或限制受邀域名，但不在本期范围。
- 邮件是至少一次投递（ADR-0006），同一邀请可能收到重复邮件；
  链接本身幂等，重复点击只会在第一次成功。
- 没有批量邀请、没有邀请备注/欢迎语、撤销时不通知被邀请人；
  这些都可以在不变更令牌模型的前提下追加。
- 管理员看不到已接受/已撤销的历史（列表只展示待接受含已过期）；
  需要完整历史时走审计日志。
